# 当前可见性模型与训练流水线

更新时间：2026-07-31

本文解释当前方向遮挡代理模型的结构、监督、训练模式和前端导出。这里的“实例特征”是每个实例一行的固定运行表，不等于 GLB 文件特征；多个实例可以复用同一个 GLB，但仍然根据实例的空间位置、尺寸和方向证据生成各自的运行特征。

## 1. 模型输入与输出

训练样本以一个 pose 集合为单位。一个 pose 是一个后退相机查询状态，包含相机位置、朝向、视场相关的水平/垂直切线值，以及该相机下的候选实例集合。候选集合中的每个实例有：

- 实例编号；
- 世界坐标 AABB；
- 所属 GLB 编号；
- 真实可见标签；
- 可见权重；
- 方向遮挡证据查询值。

模型对每个候选实例输出三个相互关联的分数：

1. **可见性分数**：用于判断实例是否进入最终候选显示集合。
2. **视觉效用分数**：估计该实例对当前画面和可见集合的相对价值。
3. **GLB 下载优先级**：用于同一 GLB 的请求、解码和缓存排序。

可见性头和两个资源调度头共享同一个实例查询特征，因此下载排序不是前端把可见性阈值结果简单聚合后的后处理；实例级渲染和 GLB 级下载仍然保留各自的输出粒度。

## 2. 离线实例几何编码

离线几何编码器是一个 PointNet++ 风格的实例点云编码器。它的输入不是浏览器加载的原始点云，而是离线从 GLB 几何中采样并与实例 AABB 属性拼接的点特征。当前每个实例最多使用 64 个采样点，单点输入为 16 维，其中包括局部点坐标、归一化场景坐标、实例中心和尺寸等信息。

编码步骤如下：

1. 在实例点集中等间隔选择最多 24 个中心点。
2. 对每个中心点按三维距离选择最多 12 个近邻。
3. 将近邻点的原始点特征与相对中心坐标拼接，经过局部多层感知器。
4. 在近邻维度上同时做均值池化和最大池化，再经过局部融合层。
5. 在中心点维度上再次做均值池化和最大池化，经过全局融合层，得到 96 维几何特征。

这里的“视角无关”指编码阶段只使用实例自身几何、AABB 属性和场景归一化信息，不读取当前相机。它不是说最终预测与视角无关：相机视线会在后续查询头中调制固定特征。

当前实现是 PointNet++ 风格的轻量局部聚合，而不是完整的标准 PointNet++ 分层采样库。中心点采用稳定的等间隔索引，近邻采用批量距离和 top-k，便于离线批量计算和结果复现。代码入口是 `current_pvs_utils.py` 中的 `InstancePointNetPPGeoEncoder`。

## 3. 方向遮挡证据与两个输出头

对每个目标实例，离线证据表按“方向单元 × 深度层 × 来源实例”组织。当前默认配置为：

- 8 个方向单元；
- 3 个深度层；
- 每个方向/深度单元最多 8 个来源实例；
- 每个来源保存来源实例编号、证据分数和聚合强度。

来源实例不是简单的固定 K 近邻。它来自离线投影几何证据：对于一个目标实例，按相对方向和深度层组织可能在该方向提供遮挡证据的实例，再保存每个单元中分数最高的有限数量来源。这样相机变化时，运行时可以在方向代理表中软选择当前相关单元，而不必为每个候选重新查询八个动态图邻居。

方向证据编码使用以下步骤：

1. 复用目标和来源实例的 96 维几何特征。
2. 拼接目标/来源的归一化中心、尺寸、相对位移、距离、尺寸比、来源分数和是否共享 GLB 等边特征。
3. 用边多层感知器生成来源消息。
4. 按来源证据分数加权池化，得到每个方向/深度单元的消息。
5. `context_head` 对所有方向和深度消息做均值/最大聚合，输出 64 维实例上下文特征。
6. `proxy_head` 对每个方向和深度单元结合目标节点、聚合消息、证据强度和方向编号，输出 8 维遮挡代理。

因此每个实例的运行表由三部分组成：

```text
96 维几何特征
+ 64 维上下文特征
+ 8 × 3 × 8 = 192 维方向遮挡代理
= 352 维固定运行特征
```

如果训练时需要显式更新离线编码器，模型会从点云输入重新计算这三部分；如果使用 `--fixed-runtime-features --freeze-offline-encoder`，训练只更新相机查询和输出头，固定特征表作为输入。无论采用哪种训练路径，浏览器端都只消费导出的固定表。

## 4. 相机条件化查询

运行时对每个候选实例构造当前相机到实例中心的单位视线方向，并计算六个轻量射线空间标量：归一化距离、视线与相机前向夹角、水平屏幕位置、垂直屏幕位置、水平角尺寸和垂直角尺寸。方向使用 10 组 Fourier 特征，标量使用 4 组 Fourier 特征。

默认不把相机世界坐标作为主要记忆输入，`camera-location-dim` 为 0。可选的低维归一化位置只作为辅助消融，不能替代视线方向查询。这样模型学习的是“固定实例表在当前视线下如何被查询”，而不是对某些相机坐标做位置记忆。

相机查询首先用一个门控层对 8×3 个方向/深度单元做 softmax，得到当前实例的 8 维遮挡代理。之后用视线方向门控对 168 维查询特征进行轻量调制：

```text
查询特征 = 96 维几何 + 64 维上下文 + 8 维选中遮挡代理
          = 168 维
```

可见性多层感知器把射线空间特征、查询特征以及二者的逐通道交互映射为基础可见性 logit。遮挡抑制头再根据查询特征与相机特征输出 0 到 4 的抑制量，最终可见性 logit 为：

```text
最终 logit = 基础可见性 logit - 遮挡抑制量
```

这使遮挡代理真正参与可见性判别，而不是仅作为训练时的旁路监督。

## 5. 损失组成

训练总损失由可见性集合目标、遮挡代理目标、视觉效用、GLB 优先级和参数正则组成。

### 5.1 可见性集合损失

`pose_set_visibility_loss_with_importance`（或 calibrated 模式）以整个 pose 的候选集合为单位计算：

- 带可见权重和漏检惩罚的 BCE；
- Tversky 集合损失，给漏掉的可见实例更高代价；
- 预测数量约束；
- pose 内正负样本排序损失。

calibrated 模式额外约束可见正样本和困难负样本的 logit 区间，防止单纯降低阈值获得高召回。

### 5.2 RVL 可见性损失

RVL 是放在可见性主损失中的排斥式可见性损失。它对每个 pose 同时处理：

- 可见实例的软漏检项，按可见权重提高重要实例的保护；
- 不可见实例的软误报项，对方向遮挡证据高、或 GLB 成本高的负样本增加惩罚。

当前正式主线使用 `rvl-mode=evidence`，因此负样本权重会随离线遮挡证据增加。它不是 dynamic-pool teacher：RVL 直接使用 GT 可见标签、离线投影证据和成本信息形成可解释的权重，不需要一个失败的动态图模型提供伪标签。

### 5.3 预测数量预算损失

对每个 pose 计算预测概率总量。如果它超过 `GT 可见数量 × 安全倍率`，只惩罚超出部分。该损失控制高召回训练中的过预测，但不会用硬约束压低召回。

### 5.4 遮挡代理证据损失

遮挡代理损失对不可见候选的预测抑制量与离线证据强度做 Smooth L1 对齐，同时包含两项约束：

- 可见保护：有 GT 可见标签的实例不应被遮挡抑制头过度压低；
- 稀疏约束：没有明显遮挡证据的不可见实例不应产生无理由的大抑制量。

它的作用是让遮挡分支学习“哪些方向/深度单元确实有遮挡解释”，并把这类解释传递到最终可见性 logit；它不是直接预测可见标签，也不能单独作为模型效果指标。

### 5.5 困难遮挡负样本排序

在同一 pose 内，把 GT 不可见且证据较高的候选作为困难负样本，要求其 logit 低于可见实例。该项补充逐点 BCE 对样本不平衡的不足。

### 5.6 视觉效用与 GLB 优先级

视觉效用目标由可见权重的对数归一化得到，并对同一 pose 内的高价值可见实例与零价值实例施加排序约束。GLB 优先级损失在 GLB 聚合层面结合可见权重、所属 GLB 成本和 pose 内正负关系，训练一个与可见性共享查询特征的下载头。

这两个头不把“GLB 是否包含阈值下可见实例”当作唯一监督，因为那会把实例级显示错误直接传播到资源级决策。其目标是优先下载能降低画面缺失、具有较高视觉效用且成本可接受的资源。

### 5.7 当前 profile 与正式权重

训练脚本支持 `legacy`、`balanced_v2`、`rvl_strong_v2`、`rvl_calibrated_v3`、`budget_tight_v2` 和 `proxy_light_v2`。脚本默认 profile 是 `balanced_v2`，但 HKUST 正式保留 checkpoint 的参数快照是 `legacy` CLI 数值加 `rvl-mode=evidence` 与 `rvl-loss-weight=0.42`。文档和论文引用正式模型时必须以输出目录中的 `model_meta.json`、`best.pt` 和训练日志为准，不能只看脚本默认值。

## 6. 训练、校准和导出

训练前依次检查：

1. Pose CSR 数据集和 `dataset_meta.json` 存在；
2. `visible_ids` 是 `candidate_ids` 的子集；
3. 运行时元数据的实例数、AABB 和实例到 GLB 映射一致；
4. 点云特征行数覆盖全部实例；
5. 遮挡证据的方向数、深度层数和来源数与模型配置一致。

训练期间每个 epoch 写入 stdout/stderr、`train_metrics.jsonl`、checkpoint 和 `train_history.json`。验证阶段扫描阈值网格，严格筛选 `weighted recall > 0.99` 的工作点，再选择 `pose precision` 最高者保存为 `best.pt`。普通 pose recall、F1、预测数量、useful cull 和 bad cull 继续记录，但不再作为第一道筛选条件；若没有合格工作点，流程不会用不安全阈值覆盖已有 best model。

导出阶段重新计算 best checkpoint 的固定特征表，生成：

- 几何、上下文、遮挡代理和完整运行特征表；
- WebGPU 所需的 FP16 权重；
- AABB、实例到 GLB 映射和模型结构布局；
- 阈值、FOV、工作点和数据语义。

导出目录的运行 schema 为 `directional-occlusion-proxy-scheduler-v1`。浏览器不需要训练端点云、证据来源实例列表或 PyTorch checkpoint。

## 7. 当前结果与限制

HKUST FOV66 当前按新规则选择的工作点为阈值约 0.64，在 684 个 test view-cell 上达到 pose precision 0.8156、pose recall 0.8680、weighted recall 0.990071、pose F1 0.8160，平均预测实例 186.63。它满足严格的 weighted recall 条件，并在当前扫描网格中具有最高 pose precision；旧阈值约 0.01 的 0.9552 pose recall / 0.9962 weighted recall 仍作为高普通召回诊断点保留，不再作为默认阈值。以上数字不代表跨场景泛化结果；两个运行时模型统一采用前端 60°、模型 66°的 FOV 契约。

当前模型的正式缺口是完整同位姿图像评价和跨场景留一验证。后续报告必须同时列出 pose/aggregate 指标、weighted recall、useful cull、bad cull、GLB 字节节省和前端延迟，不能用 best-F1 一个数字代表系统能力。

### 7.1 资源语义审计：HKUST 点云缓存

当前 HKUST 输出目录中的 `instance_features_meta.json` 记录点云缓存为 3,273 行、每行 1,024 个三维点，而运行时实例数为 18,831。模型实现的 `point_features()` 直接按实例编号访问点云缓存；当前训练前校验也要求点云行数至少覆盖实例数。两者存在语义不一致，意味着现有 HKUST 权重是历史生成产物，不能仅凭 README 命令宣称可以用当前源码严格复现。

后续重新训练 HKUST 前必须二选一并在元数据中固定：

1. 生成真正按实例编号对齐的点云缓存；或
2. 明确在模型中按 `instance_to_glb[instance_id]` 读取 GLB 原型点云，并重新校验共享 GLB 实例的 AABB/姿态条件化逻辑。

Metropolis 当前点云缓存记录为 41,298 行，与实例数一致。这个问题不改变浏览器对已经导出的 FP16 特征表的读取方式，但会影响 HKUST 训练复现、论文中“每实例几何编码”的表述以及后续跨场景实验，必须在正式重训前解决。
